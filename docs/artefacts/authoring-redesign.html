Author the variable, not the plumbing

Wiring one value between two repos today takes five edits across four editor sections. A real repo has a dozen or more of these values. This page looks at five ways to cut that down, and at whether Aspire should do the heavy lifting instead.

Examples use neutral names: shop, catalog, billingAspire facts checked against 13.2–13.6 docs and the 2026→27 roadmap
The problem

One variable, five edits, two repos

Say the shop front end needs VITE_API_URL to point at its workspace's own catalog API. In the current model you go through these steps:

catalog repo editor · module api

1
Providescapability: catalog · ports: { port: true }
2
Provides → derivedurl = http://localhost:${sprig.catalog.port}
3
Env overrides · .envPORT = ${sprig.catalog.port}

shop repo editor · module web

4
Needscapability: catalog
5
Env overrides · .env.localVITE_API_URL = ${sprig.catalog.url}

A Docker port adds a sixth edit: a compose override addressed by YAML path segments, ["services","postgres","ports","0"].

5edits for one value
4editor sections visited
3times you type the name catalog
~40form rows for a 12-variable module

The capability model is sound. Matching by name, nearest-wins, and maps that only store deviations all hold up. The friction is in authoring order. The editor asks you to think in capabilities first (provides, then needs, then env rows that reference them). But you start from the env file you already have: this key should get that value. Steps 1, 2 and 4 carry no information the env row doesn't already imply.

So the question for every option below: can the user author only the env row and have provides and needs fall out of it?

A

A variables sheet per repo

Low riskSame file format

Replace the PROVIDES / NEEDS / ENV / COMPOSE sections with one table: every env key and compose value the module touches, one row each. Each row has a source, and choosing a source writes the provides and needs for you. Choosing New port creates the provide. Choosing catalog.url creates the need. Provides and needs become a read-only summary.

For

  • Starts from what the user has open: the env file.
  • One edit per variable. Provides and needs are never typed by hand.
  • The "in workspace" column previews the resolved value before checkout.
  • Compose rows read as redis · ports[0], not path-segment arrays.
  • No schema change. It writes the same .sprig.json.

Against

  • A provide that nothing in its own repo uses (a pure export) needs a home. Keep a small "Exports" panel.
  • Shapes such as url still have to be defined somewhere. The sheet can offer "make this a shape other repos can use" on any templated row.
  • A large rewrite of the editor in ReposView.axaml.
B

Infer the wiring, then review it

Low riskPairs with A

Add-repo already scans each repo for port-shaped values. Run the same scan across all repos on a map and match values. When shop has VITE_API_URL=http://localhost:5000 and catalog has PORT=5000, the link is almost certain. Authoring becomes approving a list of links.

shop · SMTP_PORT=1025 → nothing on the map shared
Nothing provides 1025. Keep it shared as a constant, or add the mail repo.

For

  • For a large existing repo, most of the 12 variables are wired in one pass.
  • Uses information sprig already has: env files, templates, compose port maps.
  • Each accepted row writes ordinary config. Nothing new to learn.

Against

  • Only works where the committed files carry real local values. A blank .env.template gives nothing to match.
  • Port collisions in the source files (two repos defaulting to 5000) make false matches. Those must stay "maybe", never auto-accepted.
  • Helps the first setup most. Later edits still go through A.
C

A flatter file: schema 2

MigrationHelps CLI and agents

For people who edit .sprig.json by hand, or have Claude edit it. Key the file by env file and variable. Drop the ${sprig.} prefix. Infer needs from references. Write compose paths as dotted strings. The model underneath is the same, so schema 1 files migrate mechanically and the sheet in A reads and writes either.

catalog/.sprig.json · schema 127 lines
{
  "schema": 1, "name": "catalog",
  "modules": [{
    "name": "api", "path": "apps/api",
    "provides": [
      { "capability": "catalog",
        "ports": { "port": true },
        "shapes": { "url":
          "http://localhost:${sprig.catalog.port}" },
        "open": "url" },
      { "capability": "db",
        "ports": { "port": true } }
    ],
    "needs": [ { "capability": "billing" } ],
    "env": [{ "file": ".env", "set": {
      "PORT": "${sprig.catalog.port}",
      "BILLING_URL": "${sprig.billing.url}",
      "Db": "Host=localhost;Port=${sprig.db.port}"
    } }],
    "compose": [{ "file": "docker-compose.yml",
      "overrides": [{
        "path": ["services","postgres","ports","0"],
        "template": "${sprig.db.port}:5432" }]
    }]
  }]
}
catalog/.sprig.json · schema 215 lines
{
  "schema": 2, "name": "catalog",
  "api": {
    "path": "apps/api",
    "ports":   { "http": true, "db": true },
    "exports": { "catalog": { "url": "http://localhost:{http}" } },
    ".env": {
      "PORT":        "{http}",
      "BILLING_URL": "{billing.url}",  // need inferred
      "Db":          "Host=localhost;Port={db}"
    },
    "docker-compose.yml": {
      "services.postgres.ports[0]": "{db}:5432"
    }
  }
}

For

  • Roughly half the lines. One line per variable.
  • Reads top to bottom like the env file it controls.
  • Easier for Claude and the plugin to write correctly. Fewer names to keep in sync.
  • Same resolver. Only the loader and validator change.

Against

  • Two schemas to support for a while, with an automatic upgrade.
  • Using file names as keys mixes namespaces. Reserve path, ports, exports, setup, and require a file key to contain a dot.
  • On its own it doesn't help GUI users. It pairs with A.
D

Annotate the files in place

Breaks the one-file rule

Put the binding next to the value it controls, as a comment in the committed template or as a compose x- extension field. No config file to cross-reference, and the binding shows up in the same PR diff as the value.

apps/web/.env.template
PORT=5173                            # sprig: port web 8100-8103
VITE_API_URL=http://localhost:5000     # sprig: catalog.url
VITE_BILLING_URL=http://localhost:5100 # sprig: billing.url
VITE_REALM=storefront-dev
docker-compose.yml
services:
  redis:
    image: redis:7
    ports: ["6379:6379"]
    x-sprig:
      ports[0]: "{cache.port}:6379"

For

  • Nothing to cross-reference. The binding sits on the line it changes.
  • Compose ignores x- fields, so the file stays valid.

Against

  • Ends ".sprig.json is the only file sprig adds". Teams that object to tool noise will object more.
  • Many repos never commit an env file, so the comments have nowhere to go.
  • Parsing comments is fragile, and the GUI would have to rewrite other people's files.
  • Virtual repos can't use it at all.
E

Config as code, Aspire style

High cost

A sprig.ts (or sprig.cs) in each repo that sprig runs to get the model. You get loops, helpers, typed references and refactoring, which are useful for a repo with 30 near-identical variables.

catalog/sprig.ts
import { repo } from "@sprig/config";

export default repo("catalog", r => {
  const api  = r.module("api", { path: "apps/api" });
  const http = api.port("http");
  const db   = api.port("db");
  const billing = api.need("billing");           // typed handle, checked at resolve

  api.export("catalog", { url: r.fmt`http://localhost:${http}` });
  api.env(".env", {
    PORT: http,
    BILLING_URL: billing.url,
    Db: r.fmt`Host=localhost;Port=${db}`,
  });
  api.compose("docker-compose.yml").set("services.postgres.ports[0]", r.fmt`${db}:5432`);
});

For

  • Scales to very large repos: loops, shared helpers, find-references.
  • Familiar to anyone who has used an Aspire AppHost.

Against

  • Sprig would run repo code at checkout. Config is pure data today. Running code turns a pooled checkout into executing whatever is on that branch.
  • Needs Node or .NET on the machine just to read config, which the CLI avoids today.
  • The GUI can't edit code and write it back. Repos, Maps and the add-repo scan would all go read-only.
  • Code wants direct object references across repos. That drifts toward the central orchestrator sprig avoids on purpose.

Should Aspire do the heavy lifting?

Aspire has closed part of the gap

What changed since sprig's last comparison (Aug 2026): Aspire 13.2 added aspire run --isolated for running several copies of one AppHost at once, explicitly for git worktrees and parallel agents. TypeScript AppHosts went GA in 13.4, with Python, Go, Java and Rust hosts available too. The 2026→27 roadmap lists multi-repo apps and launch groups ("start only what you need"). "Aspire runs one instance at a time" is no longer true.

Three ways to integrate

1 · Live alongside it

Recommended

Sprig handles the workspace. If a repo has an AppHost, Aspire runs what's inside it.

  • Detect apphost.cs, apphost.ts or an AppHost project at add-repo and mark the module.
  • Pass sprig's leased ports in as AppHost parameters, so ports stay stable and pinned sets still work.
  • Add sprig ws run → aspire run --isolated in that worktree.
  • Sprig keeps worktrees, branches, pool and cross-repo wiring.

Small. Speaks to the ".NET shop" question directly.

2 · Import an AppHost

Fragile

Read an AppHost's resource model to fill in a .sprig.json.

  • The JSON manifest is the only export. Docs now keep it mainly for azd and point new work at aspire publish.
  • Needs the AppHost to build and run, which brings back E's problem of running code.
  • Expressions like {api.bindings.http.url} do map well onto {catalog.url}.

Medium. Worth a spike only if 1 gets real use.

3 · Rebuild on Aspire

Not now

Sprig becomes a worktree and pool manager around aspire run --isolated, and the AppHost does the wiring.

  • Every map would need an AppHost program. That's the central orchestrator sprig chose not to require.
  • Loses non-Aspire repos, IDE-launched apps, .env output, stable and pinned ports, and existing compose files.
  • Multi-repo and slices are still roadmap items in Aspire.

Revisit if Aspire ships multi-repo and launch groups and documents volume isolation.

Recommendation

Fix the authoring order, and live alongside Aspire

Build A, the variables sheet, first

The biggest drop in friction for no format change. Provides and needs become output, not input. Keep a small Exports panel for shapes other repos consume.

Feed B into it

Value-matched suggestions show up as amber rows in the sheet and as a one-time review when a repo joins a map. Never auto-accept a "maybe".

Design C alongside, and ship it once the sheet is stable

Schema 2 is the sheet's serialised form. Shipping both from one design keeps the GUI and the file describing the same thing. Add an automatic upgrade from schema 1.

Add Aspire level 1

Detect an AppHost and run it with --isolated, using sprig's leased ports. This turns "why not just Aspire?" into "use both". Sprig handles the workspace; Aspire handles running and observing it.

Leave D and E out

Both break properties sprig depends on: one file, pure data, and a GUI that can write what it reads. Revisit E only if very large repos still struggle after C.

Open question before building level 1: does Aspire's isolated mode separate container volumes? If it doesn't, two isolated runs share a database. That's the strongest remaining reason for sprig to own the compose side.
