Design proposal · desktop app front door

sprig should open on a goal, not a database table.

Today the app is three tabs — Repos, Stacks, Workspaces — that mirror the three files in the central store. That's honest to the schema and useless to a newcomer: they land on the last step of a pipeline they can't see. This proposes a Home front door plus the supporting artefacts to make the path from nothing to a running isolated instance self-evident.

Avalonia · dark-only · MVVM Engine unchanged — UI & IA only Palette from App.axaml
01

What the schema-first layout costs a new user

The nav names the store's tables. The user arrives with a job to do, and nothing on screen is in the shape of that job.

Lands on the finish line

The default page is Workspaces — the final step. A first-run user sees “No workspaces yet… create your first from a stack,” but they have no stack, and no repo to put in one. The one thing they can reach is the one thing they can't yet do.

The order is invisible

Repo → Stack → Workspace is a hard dependency chain, but the nav presents three peers. You learn the order by failing: click New workspace → “pick a stack (define one in the Stacks tab first).”

Vocabulary is the system's, not the user's

“Stack,” “bindings,” “inputs,” ${sprig.ports.*} — the producer→consumer model is elegant, but it lives only in the README. Nothing in-app teaches why the pieces relate.

Empty states hint, they don't guide

Each tab has one line of hint text pointing at its own button. None points upstream (“stacks need repos — add one first”), so a stuck user has to reverse-engineer the sequence themselves.

CORE

The tabs answer “how is sprig's data structured?” The newcomer is asking “how do I get my project running in isolation?” Everything below re-poses the app around the second question — without hiding the first from power users.

04

The artefact set

Home is the container. These are the reusable pieces that make it — and the existing tabs — read as a journey. Each is small and independently shippable.

ARTEFACT B

The journey rail

A three-node pipeline — Repos → Stacks → Workspaces — with live counts and per-node state (done / next / to-do). Numbering is earned here: it's a real ordered dependency, not decoration.

FixesThe invisible order becomes the primary visual. You always see where you are and the single step in front of you.
ARTEFACT C

Adaptive next-best-action

One banner derived from store state: 0 repos → “Add a repo”; repos but no stack → “Wire a stack”; stack but no workspace → “Spin up a workspace”; all set → “New workspace.”

FixesReplaces learn-by-error. There is always exactly one obvious right click.
ARTEFACT D

Guided “Set up sprig” wizard

An optional stepper that sequences the modals you already have — Add repo → (init .sprig.json if missing) → Build stack → Create workspace — enforcing the order the tabs hide. Skippable at any step.

FixesThe first-timer gets rails; the returning user ignores it. Reuses existing views — mostly orchestration.
ARTEFACT E

Upstream-aware empty states

Downstream tabs point back up the chain. Stacks with no repos: “Stacks compose registered repos — you have none yet.” with an Add a repo button that opens the Repos flow inline.

FixesA stuck user is never told to do something they can't yet do; the empty state is the fix, not a dead end.
ARTEFACT F

In-app mental-model card

The producer→consumer “one picture” from the README, shown on Home and behind a persistent ? affordance. Explains why values flow stack → repo, in the app, when it's relevant.

FixesThe model becomes learnable without leaving the app or reading docs.
ARTEFACT G · optional

Single-repo fast path

Surface the CLI's ad-hoc create --repo <path> as a one-click “Isolate just this repo” on Home — no stack required for the trivial single-repo case.

FixesLets a first-timer feel the payoff in one step, before learning stacks and bindings at all.

07

If we build it in order

Ranked by clarity-per-effort. The first two are small and land most of the value; the engine is untouched throughout.

  1. Reorder + group the nav, add a Home item, land there by default. Pure XAML/VM. Kills the “lands on the last step” bug on its own.
  2. Home = journey rail (B) + next-best-action (C). Both are read-only projections of state you already load. This is the front door.
  3. Upstream-aware empty states (E) + mental-model card (F). Copy and a small reusable control; no new flows.
  4. Guided wizard (D). Orchestration over existing modals + the inline init step. Highest effort, best first-run.
  5. Single-repo fast path (G), if wanted. Exposes an engine path the CLI already has.
