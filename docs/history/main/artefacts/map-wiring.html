Map wiring, at a glance

Today a map's missing pieces only show up when a checkout fails with unmet needs. This view draws the map as a dependency graph: each module sits above what it relies on, so a shared service shows up as one node with arrows coming in from every module that needs it, and a need with nothing behind it ends in a red placeholder.

What it would take

Already in Core

The wiring itself

MapGraphProjection already sorts each need into wired, ambiguous or gap, using the same rules as checkout, and produces the module-to-module edges. The app only uses it for the partial-checkout hint today. The graph is that projection, laid out.

Layout in the app

Layered, with repos as boxes

Nodes are modules, edges are needs, and each repo with more than one module is a box around its modules. A layered (Sugiyama-style) layout places consumers above providers and keeps crossings down; this page uses dagre for that. In the Avalonia app, the MSAGL library (Microsoft's graph layout, MIT licensed, on NuGet) is a candidate to compute positions for a canvas to draw.

New readings

On top of the projection

  • How many modules rely on each provide, so shared services stand out.
  • Near misses: a gap whose name is close to an existing provide (account-api vs accounts-api), offered as a map wiring entry.
  • A value hint for a gap, read from the module's env templates.
  • Fixed values: env settings that pin a localhost port or address instead of using a need.
  • sprig map check <name> exits non-zero on gaps or ambiguity, for scripts and CI.
Already supported

Giving a need a constant value

  • Set it on the map. defaults[repo][capability][output] in the map file. Used only when nothing in the map provides the need, so a real provider always wins. Drawn as a violet node, like billing's payments-gateway.
  • Provide it from a module. A capability with a fixed shapes value and no port, like auth's realm. Every module that needs it gets the same value. Drawn with a ◆.
  • Per checkout. Core's checkout accepts one-off values tried before the map's, but nothing in the app or CLI passes them in yet.
"defaults": {
  "billing": {
    "payments-gateway": { "url": "https://pay.sandbox.test" }
  }
}
Gap in the model

Ambiguity can't be resolved yet

When two repos provide the same capability, checkout says to add a map wiring entry. But a wiring entry maps a need to a capability name, so it can't choose between two repos that use the same name. The storefront example's cache shows this. The map needs a way to name the providing repo.
