Sprig · design exploration · stack wiring

Wiring a stack should feel like
patching cables, not filling a form.

Defining a stack today means binding every input of every repo by hand — and most of the time you're just typing ${sprig.ports.api_port} into yet another box. The work only gets interesting in two places: when two repos share one port, and when a value needs a transform (a port becoming a URL). This document proposes a ladder of UX moves that make the boring 80% disappear and put the two interesting cases front and centre — ending with a graphical patchbay you can wire by hand.

01
The problem

The wiring stage reads as repeated work

A stack has three real repos below. The binding editor asks you to fill one token box per declared input. Look how much of it is a name → same-named port identity mapping — busywork the tool already has enough information to propose itself.

Nothing on screen tells you that port and apiUrl resolve to the same allocated port, or that dbPort appears in two repos. The relationships that actually matter are invisible; the parts that don't matter take all the clicks.

02
Design principles

Three ideas everything else follows from

A

Propose, don't prompt

The identity mapping (input port → port port) is the default. Sprig should pre-wire it and let you glance-and-accept, not type it.

B

Spend attention on exceptions

Collapse the mechanical rows. Surface only the two things worth a human decision: a shared port and a transform.

C

Make the graph visible

Sharing is a relationship between repos. A list can't show it; a wiring surface can. Ports are producers, inputs are consumers, cables are bindings.

03
A ladder of moves

From a quick win to a full canvas

Each rung stands on its own and ships independently. Effort rises as you go down; so does how much it changes the feel.

1 Effort
Ships on today's form

Auto-wire by convention

When a repo is added, match each declared input against existing (and proposed) ports by name and AllowedPorts. Pre-fill the binding, create the port if it's new, and mark the row auto. You confirm a stack instead of authoring one.

frontend←${sprig.ports.frontend_port}auto
dbPort←${sprig.ports.postgres_port}auto
queuePort←${sprig.ports.queue_port}auto
2 Effort
Ships on today's form

Collapse the mechanical, surface the exceptional

Fold every clean auto-wired row into a single confirmable strip. Keep only the rows that carry a real decision expanded — a transform, or a port two repos share.

4 inputs auto-wired to matching ports — all valid ▸ review
apiUrl←http://localhost:${…api_port}transform
port · dbPort⇄2 repos → api_port / postgres_portshared
3 Effort
Reuses SprigTokenBox

Transforms as a named module, not raw string-wrapping

The http://localhost:${port} case is really "derive a URL from a port". Offer it as a pickable transform with presets — URL from port, connection string, host:port — with the raw SprigTokenBox still underneath for anything bespoke.

api_port 8003 transform · url from porthttp://localhost:${port} apiUrl
4 Effort
New concept "share port"

Make "share a port" an explicit verb

Instead of hoping two people type the same port name, add a link action on any input: "consume the same port as…". Both bindings then track one port; renaming or reallocating it updates both. The shared relationship becomes data, not a coincidence of strings.

dotnet-api · port⇄linked to → worker is freesource
worker · upstreamApi⇄follows dotnet-api · portlinked
5 Effort
Greenfield Canvas + Shapes

The patchbay — wire the stack by hand

The full graphical move. Ports run down a central rail as producers; repos sit either side with an input pin per declared input. Drag a pin to a port to bind it. Shared ports show as cables converging; transforms live on the cable. Try it below.

Live mock of idea 5. Hover a port to see everything wired to it (the shared-port relationship, made visible). Hover the pink cable for the transform. 06
Recommendation

Sequence the wins

Ship the cheap, high-impact moves on the existing form first — they remove most of the felt busywork without a rewrite — then treat the canvas as a second, opt-in view once the data model already supports explicit sharing.

  1. Auto-wire on repo add.

    Convention matching against ports + AllowedPorts. This alone removes ~80% of typing. Reuses today's binding rows.

  2. Collapse valid rows, expand exceptions.

    One confirmable strip for clean mappings; transforms and shared ports stay open. Pure view change over the same bindings.

  3. Transform modules + explicit "share port".

    Turn the two interesting cases into named, first-class actions. "Share" makes the relationship real data — the prerequisite for a faithful canvas.

  4. Patchbay as an opt-in view.

    Built on Avalonia Canvas + Shapes, reading the now-explicit graph. A toggle beside the list, not a replacement for it.
