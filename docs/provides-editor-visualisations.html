One name, many shapes

A capability isn’t a name plus a bag of outputs. It’s a single name that shows up in several shapes — a port, a URL, a connection string. Three ways to make the editor say that out loud.

Where it’s blurry today

The name and its outputs look like the same kind of thing

The current editor stacks a capability’s name next to its outputs on a flat plane, and hangs a lonely port checkbox off each output. Nothing on screen tells you the name is the parent and the outputs are its shapes — so ${sprig.…} never comes into focus.

  • The capability name row and the output name rows use the same field styling — the hierarchy is flat, so which is the variable and which are its shapes isn’t readable.
  • The port checkbox sits at the output level with no anchor. “Is the capability a port? Is this row a port?” It reads as a mystery toggle.
  • Nothing steers naming, so ${sprig.vite-port.port} — the stutter — is the path of least resistance.
The reframe

Lean on the reference: ${sprig.<name>.<shape>}

Every consumer types the same two-segment token. The name is the thing you’re wiring to; the shape is which form of it you want. One name, resolved into as many shapes as the service exposes:

${sprig.vite-server.port} ${sprig.vite-server.url} ← same head, different shape

And a naming rule that falls out of it: name the service, not the socket. The shape already says port — the name shouldn’t say it again.

✓ reads as a hierarchy
${sprig.vite-server.port} ${sprig.vite-server.url}

The service is vite-server; it comes in a port shape and a url shape. The name owns both.

× the stutter
${sprig.vite-port.port} ${sprig.vite-port.url}

Naming the capability after one of its shapes gives you vite-port.port, and makes vite-port.url read as nonsense.

A

The token, made literal

The capability header is the reference stem. You edit the name inside a live ${sprig.___} chip; each shape below it renders its own full token, so the hierarchy is impossible to miss. The port checkbox becomes a two-state kind toggle per shape — port or derived.

Provides — option A

${sprig..…} http
PORT · allocated ${sprig.vite-server.port}
DERIVED ${sprig.vite-server.url}

Strengths

  • The name lives inside the actual token — the parent/shape relationship is literal, not implied.
  • Consumers see the exact string they’ll type, per shape.
  • “+ port / + derived” replaces the ambiguous checkbox with an explicit choice at creation.

Trade-offs

  • Repeating ${sprig.vite-server.} on every row costs horizontal space.
  • An editable field nested inside a token chip is a slightly unusual control to build in Avalonia.
B

The port is the anchor

A service really owns exactly one real thing: a port. So lead with it. The name sits atop a single, always-present Port — the root — and everything else is filed under “Also exposes” as formulas over that port. There is no checkbox at all: port is structural, derived is an addition.

Provides — option B

http
PORT .port

also exposes — formulas over the port

DERIVED .url

Strengths

  • Encodes the truth of the model — a port is the one owned resource; the rest are views of it.
  • Kills the checkbox entirely; nothing to misread.
  • Puts the name directly above its port, which quietly enforces the naming rule.

Trade-offs

  • A capability with no port (a pure derived value, or an externally-fixed one) is the awkward case — needs an “extra port” / “no port” escape hatch.
  • Two-tier layout (anchor vs. “also exposes”) is more structure to build than a flat list.
C

Shape-kind picker

The lightest-touch change: keep the flat row-per-output table, but replace the bare port checkbox with a segmented kind picker. Now port is one shape among several, and the type hint finally earns its keep — choosing URL or Connection string pre-fills a sensible formula.

Strengths

  • Smallest diff from today’s layout — low build cost, low risk.
  • Presets (URL, Conn str) teach the common formulas and cut typos in templates.
  • Gives the type hint a real job: seeding the shape presets.

Trade-offs

  • Still a flat table — does the least to surface the name-owns-its-shapes hierarchy.
  • Doesn’t show the resolved ${sprig…} token, so naming stays uncoached.
Where I’d land

Blend A’s literal token with B’s port anchor

Take the name-inside-the-token header from A so the hierarchy is stated in the one place everyone already reads — the reference. Take the port-as-root idea from B so the checkbox disappears and the model’s one real resource leads. That combination fixes both frictions in your feedback: the blurriness (the name visibly parents its shapes) and the naming trap (the token preview makes vite-port.port look wrong the instant you type it). Keep C’s presets as the payload of the “+ derived shape” button — a small menu (URL / connection string / custom) so common formulas are one click, not a hand-typed template.

If build cost has to be minimal for this pass, ship C alone now — it’s a near drop-in for the existing table — and grow it toward A/B once the layout work is worth it.
