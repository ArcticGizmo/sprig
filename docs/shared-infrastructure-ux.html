Sprig · design exploration · shared infrastructure · rev 2

Your machine's resources are
your business, not your repo's.

One postgres per workspace is expensive, and pooling it is worth doing. But an optimisation that only some people want must not cost the people who don't want it anything — and the first draft of this design failed that test. This revision makes a shared resource an overlay: it is defined once, machine-locally, and injects itself into any plan that matches. Nothing in .sprig.json changes. Nothing in a stack changes. Turn it off and you are exactly where you started.

01
Autopsy

What the first draft got wrong

Rev 1 said: to share a database server, the repo must stop declaring a port and start declaring a connection string, because only the stack can know the database name. Locally coherent. Globally wrong — it makes a permanent edit to a tracked file every teammate reads in order to serve a machine-local optimisation that most of them aren't using.

Rev 1 — the tax

Everyone pays for one person's pooling

was inputs: [ { name: dbPort, example: 5432 } ]
became inputs: [ { name: dbUrl, example: "Host=…;Port=…;Database=…;Username=…;Password=…" } ]

Now a developer with one worktree and a private postgres — the majority — has to author a whole connection string in their stack binding where ${sprig.ports.postgres_port} did the job. They got a worse experience so somebody else could save a container.

Rev 2 — the inversion

The optimisation carries its own cost

repo inputs: [ { name: dbPort, example: 5432 } ]  ← untouched
shared postgres-16 injects: dbPort → 5432, and rewrites the one env key that pins the db name

The knowledge that "this machine pools postgres" lives only where that's true. A teammate who clones the repo and builds the same stack gets a private postgres on an allocated port, and never learns this feature exists.

The reframe that makes it hold together

A shared resource is not a third producer that repos or stacks reference — that would break sprig's one-directional promise and put a machine-local concept into shared files. It's a transform applied to the resolved plan, after the stack has produced every value and before anything is written to disk. Values still flow one way, stack → repo. The overlay is a lens over that flow, and it is the only layer that knows it exists.

02
The layers

Three layers, one direction, strict precedence

Each layer may write over the one above it, and nothing may write upward. That single rule is what keeps a layered system explainable — and it is the rule every error message, badge and diff in this document is built to expose.

Resolution order · repo → stack → shared last writer wins · conflicts are errors, never silent
repo — tracked, team-wide stack — central store, exportable shared — machine-local overlay

What an overlay may and may not touch

TargetOperationWhy it's allowed
bindings[repo][input] replace The preferred level. If the repo already exposes the right input, override there — it's one value, it survives the repo renaming things internally, and it shows up in the wiring view.
env[file].set[KEY] replace · add The fallback when no input covers the value — e.g. a database name baked into a connection string. Reaches a layer deeper, and pays for it (see R1).
compose[file].overrides[path] replace · add Point a container at the shared host/port, or set a hostname on the shared network.
compose[file].services[name] suppress The whole reason for the feature: don't start the repo's own postgres. Prunes dangling depends_on and orphaned volumes with it.
setup[] · worktree · branch forbidden An overlay configures infrastructure. It does not get to change what code you check out or what commands run against it.

Prefer the highest layer that can express the change. sprig applies that rule itself during extraction — it looks for an input that already carries the value and only reaches down into env[].set when there isn't one, and it tells you which it picked and why.

03
The centrepiece

Every value says which layer produced it

A hidden layer that quietly rewrites values is a debugging trap unless you answer one question instantly: why is this value what it is? So the plan is a first-class, inspectable object — shown before create, stored on the workspace, and printable at any time. Every entry carries a layer chip and, when it was overridden, the value it would otherwise have had.

05
Mechanics

Six things that could break this, and what stops them

Pondering the overlay approach turned up one genuinely hard problem, one required refactor, and four things that are only dangerous if handled naively. None of them is a reason not to build it; all of them shape what M0 has to contain.

R1

The coupling doesn't disappear — it flips direction

Rev 1 made the repo declare a contract (dbUrl), which was expensive but honest: the repo owner could see it. Rev 2 has the overlay reach into repo internals — a specific env KEY, a specific compose path — across a boundary the repo owner doesn't know exists. Rename ConnectionStrings__Default and the overlay stops matching. Handled naively, you'd get a silent revert to a private postgres that isn't running, and a connection error three layers away from the cause.

Fix: an override whose target doesn't resolve is a hard failure at plan time, never a skip — with optional: true as the deliberate escape. doctor validates every enabled overlay against current repo configs without needing a workspace. And the repo editor shows the reverse view — "1 shared resource overrides this key on this machine" — so the coupling is visible from both ends.

R2

Port allocation has to move

StackResolver allocates ports as part of producing a ResolvedStack. But overlays must apply before allocation, or every pooled workspace still burns a postgres_port nobody references — which quietly cancels part of the saving the feature exists for.

Fix: split resolution from allocation. resolve wiring → apply overlays → collect surviving port references → allocate. This is the real refactor in this proposal, and it's also what produces the inspectable plan object in section 03, so it pays for itself twice.

R3

A workspace must remember which overlays it was built with

Overlays are machine-local and toggleable. Toggle one off while a workspace built with it is alive, and down tries to release a slot it doesn't hold, while the repo's own postgres — suppressed at create, so never configured — is suddenly expected to exist.

Fix: the applied overlay set is pinned into the instance record at create and read from there for that workspace's whole life. Editing an overlay's definition is blocked while any workspace references it — the same rule stacks already follow.

R4

Two overlays, one target

Two shared resources both wanting to write .env → ConnectionStrings__Default is not hypothetical once you have postgres and a connection-pooler overlay. Last-writer-wins in a layer people forget exists is a very expensive afternoon.

Fix: a conflict is a hard error naming both overlays and the target. No priority field, no ordering rules — if two overlays disagree, a human decides.

R5

Two repos in one workspace, one database name

If an overlay applies to two repos in the same stack, the default sprig_${sprig.workspace} resolves identically for both — and they'd share a database inside a feature whose entire point is that they shouldn't.

Fix: detect it at plan time and say so, rather than defending against it with a cleverer default: "dotnet-api and reporting-api would both use sprig_feature_x — add ${sprig.repo} to the database template." One-click fix included.

R6

Discoverability is now the dominant UX cost

Rev 1's cost was visible and permanent (a changed tracked file). Rev 2's cost is invisible and machine-local, which is better — but it means someone will one day ask why their app is on 5432 when their stack clearly says 8034. This is the trade being made, deliberately.

Fix: section 03 is the answer, everywhere. Layer chips on every value, an "overridden" marker in the repo and stack editors, a persistent 1 shared resource active chip on the workspace, and sprig plan in the CLI.

Capacity

Slots, and the two counters that drive everything

A resource declares how many workspaces may be attached at once. Each attached workspace holds one slot, and a slot owns a namespace — a database, a vhost, a bucket, or just an index. The subtlety worth getting right: attached and running are different counters and drive different things.

Shared · postgres-16 up attached 3 / 5
attached & running attached, workspace stopped container up the workspace's own isolated resources
counter 1

Attached — create to rm

Taken when the workspace is created, held until it's removed. This is what capacity limits. It owns your data, so a stopped workspace keeps its database — exactly as it keeps its worktree.

counter 2

Running — up to down

A plain refcount over attached workspaces that are up. This is what starts and stops the container. First up provisions; last down deprovisions. Nobody waits on anybody else.

Holders are listed oldest first, so the one you've forgotten is the one you read first. The model is taught in one line rather than linked. And the last option is the one rev 1 couldn't offer: opt out and carry on, because without the overlay the stack is still a complete, valid stack.

07
Off is a first-class state

The single-worktree developer never meets this feature

This is the test rev 1 failed, so it's worth being explicit about what "off" means at every level. Some people want one docker project per tree because it's predictable and contained — that's a legitimate preference, not a failure to optimise.

ScopeHow you turn it offWhat you get
never used it Do nothing. Don't open the Shared page. Today's sprig, unchanged. No new required fields, no schema bump, no new concepts in any file you share with anyone.
one workspace sprig create x --no-shared, or the button on the plan preview. A private postgres on an allocated port for that workspace only. Recorded on the instance, so its whole lifecycle stays consistent.
one resource Toggle enabled off on the resource. New workspaces stop pooling. Existing ones keep working — they pinned their overlays at create (R3).
one stack Narrow the resource's applies to, or exclude that stack. Everything else keeps pooling. The stack file itself is never edited, so nothing leaks into your export.
your teammate Nothing to do — it was never in the repo or the stack. They clone, register the repo, build the stack, and get a private postgres. They will not find out this feature exists.

The property that makes all of this true: a stack must still be complete and valid without any overlay. An overlay may only ever replace a value that already resolves — never supply a missing one. That single constraint is what guarantees "off" is always a working configuration, and it's worth enforcing in the validator rather than trusting.

Delivery

Six milestones, risk-first

The plan refactor (R2) comes first because everything else sits on it, and because it's independently useful — sprig plan is a better debugging story than sprig has today, overlays or not.

M0foundation

The plan object, and splitting resolve from allocate

Introduce WorkspacePlan between ResolvedStack and materialisation, with per-value layer provenance. Move port allocation after plan construction so unreferenced ports can be dropped.

ships: sprig plan — layer-annotated, no overlays needed
M1overlay

The overlay engine

The shared-resource store, injects[] application over the plan, target resolution with hard failure (R1), conflict detection (R4), and the "off must still be valid" validator rule. No docker yet — this is all deterministic and unit-testable.

ships: overrides visibly change a plan
M2compose

Suppression & pruning

ComposeGenerator learns structural removal, not just scalar override: drop services, prune depends_on, drop orphaned volumes, skip a file emptied entirely.

ships: nothing runs twice
M3lifecycle

Slots, refcount, attach & detach

The two counters wired into create/up/down/rm, the lease ledger on the port store's file-lock pattern, health waiting, whenIdle, overlay pinning (R3), --no-shared. Integration-tested against a real postgres — this is the part most likely to surprise us.

ships: the feature actually saves resources
M4authoring

Extraction, presets, injection-point selection

Lift a service out of a repo compose file, detect the image, fill values and attach/detach from a preset, and pick the highest layer that can carry each value — section 04's flow, CLI first.

ships: sprig shared extract --repo … --service …
M5app

The Shared page, layer chips everywhere, doctor

Sections 03, 04 and 08: the list + detail page, the extract overlay, layer chips on every value in the workspace/repo/stack editors, the "overridden on this machine" reverse view, stale-slot nudges, and overlay-target validation in doctor.

ships: discoverable, and safe to leave running for a month
11
Decide before M0

Four questions

Is a slot held from create-to-remove, or only while running?

Create-to-remove means a stopped workspace keeps its data but keeps eating capacity. Running-only means better utilisation but a workspace that goes down and comes back may find its data gone.

Leaning: create-to-remove — you said "attached", and losing a stopped workspace's database would betray the isolation promise. Assumed throughout.

How far does "override any layer" go in v1?

Mechanically this is a patch system — it could target anything. A full patch UI is a lot of rope, and a lot of surface to explain.

Leaning: ship the general mechanism in core (it's simpler than a restricted one), but only surface resource-shaped overlays in the UI for v1. Per-workspace --set comes free and can stay CLI-only until it's asked for.

Should whenIdle default to stop or keep?

Stopping honours "deprovision when nothing is connected", but a solo user toggling one workspace pays a cold start each time.

Leaning: default stop, with keep one click away — and a nudge offering it after the third stop-start cycle in a day.

Do overlays ever get exported?

They're machine-local by design, which is the whole argument. But a team standardising on a pooled postgres would want to hand one around, and that's a reasonable thing to want.

Leaning: reuse the stack export/import shape, defer past M5, and never make import automatic — an overlay arriving without you choosing it would undo the property this revision exists to protect.
